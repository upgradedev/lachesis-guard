    Decision Fabric · Design View

    How one tool call travels

    The design as the code in this repository defines it, plus one planned part, marked as planned. This is a diagram, not a live status page.

    Before the tool runs: the synchronous decision

    1. AgentAmazon Bedrock AgentCore RuntimeRuns the Strands agent and proposes each tool call.
    2. Lachesis interventionStrands InterventionHandlerRuns the deterministic pre-checks first (safe reads, the secret scan, repeats of a refusal); for every other call it asks Decider two typed questions, then plain Python rules return Proceed, Guide, Confirm or Deny.
    3. DeciderStrands Decider 2B on Amazon SageMakerAnswers the risk class and the grounding question, each with a confidence.

    A Confirm pauses the run for a person

    1. Approvals APIAmazon API Gateway HTTP API and AWS LambdaRecords the decision on a paused call and hands start and resume to the runner Lambda, which invokes the agent and records each pause.
    2. Unit of WorkAmazon DynamoDB TransactWriteItemsWrites the run aggregate (lachesis-approvals) and its events (lachesis-run-events) in one transaction.

    After the commit: the event-driven trail

    1. Stream publisherAWS Lambda on DynamoDB StreamsRelays each new event, with a whitelisted detail, to the bus.
    2. Event busAmazon EventBridge, lachesis-eventsRoutes run events to the audit rule.
    3. Audit deliveryAmazon Data Firehose to Amazon S3Writes every event as JSON lines to the audit bucket.
    4. InsightAWS Glue and Amazon AthenaHolds the table schema and answers the audit queries.

    When something fails

    • Dead-letter queuesAmazon SQSKeep what the runner, the publisher and the audit rule could not deliver.
    • AlarmsAmazon CloudWatch to Amazon SNSNotify the alerts topic on a failed run, a dead-lettered message or late delivery.
    • Approval workflowAWS Step FunctionsWould own the wait for a person and the resume.Planned: behind a flag, not yet live
