# GPU measurement, 2026-10-13

## Headline

The same pinned Decider, served on one GPU instance for one bounded run,
answered about 71 times faster than on the CPU box, and changed no verdict.

## Numbers

Both devices answered the same 50 labeled cases in
`evaluation/threshold_cases.jsonl` against
`StrandsAgents/strands-decider-2B-qwen3.5-v1-2610` served by
strands-decider 0.1.0 on port 8099. The GPU column ran
`scripts/measure_threshold.py`; its rows are committed as
`evaluation/gpu_threshold_2026-10-13.jsonl`. The CPU column recomputes from
the committed rows in `evaluation/baseline_2026-10-13.jsonl`, where the
Lachesis handler's own `decider_ms` (median 13,728 ms over the 45 asked
cases) is the CPU figure; the CI calibration run's median was 7,437 ms
(p95 7,707 ms, n=50) on a GitHub runner (run 38421303470, 2026-10-13;
recomputed from that run's printed latency line).

- Decider-asked cases: 45 of 50 on both devices (five tier-0 reads never
  reach the model).
- Latency per asked case, median: **193 ms on GPU, 13,728 ms on CPU**.
- Latency per asked case, p95: 199 ms on GPU, 17,293 ms on CPU.
- Verdict mix on GPU: confirm 41, deny 1, proceed 3, plus 5 tier-0 proceeds.
- Suggested threshold from the pre-registered rule: 0.7 on both devices;
  held-out accuracy at 0.7: 8 of 8 on GPU.
- Verdict and risk-class parity: **0 of 50 cases differ between devices**.
  The three tour stops matched: t06 proceed benign 0.838 on GPU against
  0.833 on CPU; t20 confirm destructive_write 0.865 against 0.866; t28 deny
  exfiltration 0.841 on both.
- The pattern tour (`patterns/guardrails/example.py`) fired proceed, guide,
  confirm and deny on GPU, in 0.8 s total.

## Run

- Instance i-0320dbff137ba095f, g5.xlarge (NVIDIA A10G) in eu-west-1,
  Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04), launched
  2026-10-13T14:11Z and terminated the same hour, about $0.27 ESTIMATE
  (14.2 minutes at $1.123 per hour on demand).
- Launcher: `scripts/gpu_measure.sh` (installs strands-decider 0.1.0 and
  strands-agents, serves with `--device cuda`, clones this repo, measures).
  The repo was cloned at main 0682660; strands-agents resolved to 1.60.0 on
  the box while the CPU measurements used 1.53.0 on the laptop. Only the
  client glue differs; the model, questions and policy are this repo's.
- The user-data pass served the model but skipped the measurement (the
  repo scripts also import strands-agents, which the first install line
  missed); the install line now covers both, and the measurement plus tour
  above ran interactively against the same server. Full box log kept by the
  owner.

## What this does and does not change

The filmed demo and video run on CPU by design, and nothing above moves them:
the point of the GPU run is that the latency bonus is real and the verdicts
do not drift with the device, so a builder with a GPU gets the same gate at
about 193 ms a triage. CPU numbers elsewhere in this repository stay labeled
as CPU numbers.

Cold start, same day, from a read-back cold state (endpoint
CurrentInstanceCount 0, copy count 0, both verified with boto3 describe
calls before the first invoke; all times UTC, from CloudTrail and the
alarm histories): first cold invoke 20:34:53, failed at once with a
no-capacity error. The wake alarm fired and copy requests were issued
at 20:37:22 and 20:40:22, but the placement stalled; the endpoint
instance was up by about 20:40. A person then reset the copy request
by hand (copy count 0 at 21:02:33, re-issued immediately); the copy
placed in 98 seconds (21:03:22 to 21:05:00) and the first successful
invocations are at 21:08 (first one 1404 ms). So the honest summary is
not a duration but a behaviour: an unattended cold wake stalled and
needed a manual reset, after which placement was fast. The warm script
(scripts/set_decider_warm.py) now performs that one reset itself.

Unattended --warm drill, 2026-10-16 (script log timestamps, UTC): from
0 instances and 0 copies, --warm requested at 08:52:56 set MinCapacity
1 and DesiredCopyCount went to 1, but no instance provisioned in the
45-minute budget; the desired count later reverted to 0 and the script
exited at its deadline at 09:37:45 ("decider did not warm in 2700
seconds"). Cold invokes at 09:41 re-armed the alarm path (endpoint
Updating, instance DesiredInstanceCount 1 from about 09:44) and
SageMaker was still trying to provision ml.g5.xlarge at 10:15, so the
drill's finding is that instance capacity, not the copy, is the slow
and uncertain step in eu-west-1; the same type failed endpoint
creation twice on 2026-10-15 before succeeding. Target tracking held
no copy and therefore billed nothing during the drill (instance count
stayed 0), and the target was set cold again afterwards. Practical
consequence: warm at least two hours before a recording slot, keep
retrying through capacity, and never promise a wake time. The
earlier "about 80 s" warm figure in workspace notes referred only to
copy scale-out on an already-running instance and is withdrawn.
